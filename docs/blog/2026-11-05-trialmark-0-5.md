# Trialmark: acceptance tests for the AI model you are about to ship

*An open-source framework for evaluating language models and deciding, by a rule you fix in
advance, which one is good enough for your task. Trialmark 0.5.0, 5 November 2026.*

Every team building with a language model faces the same choice. A bigger model is usually more
accurate, but it costs more and answers more slowly. A smaller one is cheaper, but is it good
enough for *your* task? Public leaderboards cannot tell you: they test someone else's questions,
not your contracts, your support tickets or your invoices.

Trialmark answers that question with evidence from your own work. Version 0.5.0 is out today on
PyPI.

```bash
pip install "trialmark[anthropic]"
trialmark init qa
```

## Evaluation measures. Acceptance testing decides.

Most evaluation tools help you measure: they score answers and show you the numbers. The decision
about which model to ship is left to whoever reads the chart, after they have seen it. That is
where good intentions go wrong. It is easy to look at a close result and decide that the model
you already liked is good enough.

Software engineering solved this long ago with acceptance tests: the criteria are written down
before the work is judged. Trialmark brings that discipline to model choice. You write the rule
first, for example *"choose the cheapest model within 3 points of the best on correct answers,
with at least 95% of its answers grounded in the documents"*. Trialmark stores that rule, with a
fingerprint and the time it was set, before any model runs. Then it runs the test, applies your
rule and names the model that passes.

## How it works

1. **Bring your cases.** Questions or inputs from your own work, each with the right answer, in a
   CSV or JSON file. Tag them by kind, such as "simple fact" or "needs several parts".
2. **Fix the pass mark.** Write the rule in the configuration. It is saved and fingerprinted
   before anything runs.
3. **See the cost first.** `trialmark run` prints the plan and an estimated bill and spends
   nothing. Models are called only when you add `--yes`, and `--limit 3` tries a few cases first.
4. **Run every model several times.** Models do not give the same answer twice, so each model
   answers every case more than once, and the report shows the range. A difference inside the
   range is no difference.
5. **Get the decision and a record.** Accuracy, cost and speed per model and per kind of case,
   your rule applied, and one file that holds everything needed to rerun and check the test.
   `trialmark gate` turns it into a pass or a fail for your build pipeline.

This is the report from a run of the question-answering starter, two Claude models on two
questions, three repeats each, graded by a third model:

```text
Judge      claude-opus-5-5, 12 calls, $0.05
Spent      $0.01 on answers, $0.05 on the judge

Model              correct  declined  grounded  partial  Cost/100  Median time
claude-haiku-5-5   100%     0%        100%      0%       $0.01     1.1s
claude-sonnet-5-5  100%     0%        100%      0%       $0.19     3.5s

Pass mark  correct within 5 points of the best, grounded at least 90%; choose the cheapest.
  PASS  claude-haiku-5-5
  PASS  claude-sonnet-5-5
Chosen     claude-haiku-5-5
```

## What you can test

Trialmark tests any task where you can give a model an input and say what a good output is. What
changes from one kind of task to another is how an answer is marked, and each kind has a
ready-to-run starter:

| Kind of task | How it is marked | Starter |
|---|---|---|
| Answering questions from documents (RAG) | A judge model compares each answer with your right answer, and checks it stays within the documents | `trialmark init qa` |
| Extracting fields from invoices, forms, contracts | Field by field, numbers as numbers, plus a JSON Schema for the shape | `trialmark init extraction` |
| Classifying tickets, documents, intents | The label, then precision and recall for each category | `trialmark init classification` |
| Writing, summarising and analysis | A judge model marks each item of a checklist you write | `trialmark init summarisation` |
| Calculating figures | The number, within a tolerance you set | `trialmark init calculation` |
| Your own system, such as your retrieval pipeline | Any of the above, through a Python function that calls your app | [the guide](https://github.com/peshwar9/trialmark/blob/main/docs/tasks.md#testing-your-own-system-rather-than-a-bare-model) |

Each starter runs as it is, with an Anthropic or OpenAI key, and most cost well under a dollar to
run in full. [What you can test](https://github.com/peshwar9/trialmark/blob/main/docs/tasks.md) explains each kind of task in detail, and the
[starters](https://github.com/peshwar9/trialmark/tree/main/examples/starters) are in the repository.

## Which models it works with

Any model you can call from Python. Claude and OpenAI models have built-in runners. Every other
model takes a short Python function: Gemini, Mistral, models on Amazon Bedrock or Azure,
open-weight models such as Llama or Qwen run locally with Ollama or vLLM, your fine-tuned models,
even a classic text classifier.

What matters is not how a model is built but what it returns. Today Trialmark marks text, JSON,
labels and numbers. Models that return other things need their own scorers first: boxes and masks
from detection models, transcripts from speech-to-text, rankings from embedding models, and
generated images. Those are plugins, not changes to the core, and
[Which models](https://github.com/peshwar9/trialmark/blob/main/docs/models.md) says what each would need.

## How Trialmark differs from other evaluation tools

There are good open-source evaluation tools already. promptfoo compares prompts and models
against assertions and runs in CI. DeepEval brings metrics with thresholds to a pytest-style
workflow. Ragas offers metrics designed for retrieval-augmented generation. Inspect is a
framework for capability and safety evaluations of models. Hosted platforms such as Braintrust
and LangSmith add experiment tracking and tracing. Trialmark does not try to replace them. It is
built around a different question: *which model should we ship for this task, and can we prove
how we decided?*

| Trialmark's choice | Why it matters |
|---|---|
| The decision is a rule across models, fixed before the run and fingerprinted | "Cheapest within 3 points of the best" chooses between models, which a per-test threshold does not. Fixing it first stops the goalposts moving. |
| Repeats and ranges are built in | A one-point lead from a single run is often noise. The report shows the lowest and highest repeat, so you can tell. |
| Cost is a result, and a gate | Cost per hundred cases sits beside accuracy, and nothing is spent without an estimate and `--yes`. |
| The grader is checked | `trialmark judge-check` has you mark a blind sample yourself and reports how often the judge agreed. |
| Results by kind of case | A cheap model is often as good as an expensive one on simple cases and worse on hard ones. The breakdown shows where. |
| A portable record | One JSON file per run, with hashes under the RFC 8785 standard, so a program in any language can check it. JSON Schemas describe every format. |
| Runs on your machine | No account and no hosted service. The core has no dependencies; your cases and records stay with you. |

If you already use one of those tools, keep it. Trialmark's scorers are plugins, so a plugin can
wrap a metric you already trust, and Trialmark adds the pass mark, the repeats, the cost and the
record around it. *Comparisons as of November 2026; each project's documentation is the authority
on what it does.*

## Where it came from

Trialmark was spun out of the model benchmark in [Forge](https://www.forgeprivate.com), a
governed layer through which organisations delegate work to AI. That benchmark runs 42 questions
about four business documents through Forge's own answer path, on four Claude models, three times
each.

The breakdown by kind of question turned out to be the useful part. Every model answered single
facts correctly, 100% of the time. On questions with two right answers, Claude Haiku 4.5 fell to
83%, and on questions needing several clauses to 78%, while Claude Sonnet 5.5 stayed at 100%.
That is a routing rule: a cheap model for fact lookups, a stronger one for multi-part questions.

The benchmark also caught a fault in Forge itself. On a simple calculation, the two newest models
scored 0%. They were not bad at arithmetic: they were following one of Forge's own rules
literally, which forbade calculating with figures read from a document. Forge fixed the rule so
document figures can be used once each is checked against the passage it came from, and a rerun
answered correctly in all twelve attempts. An acceptance test you trust tells you when the
problem is yours rather than the model's.

## Try it

```bash
pip install "trialmark[anthropic]"            # or "trialmark[openai]"
export ANTHROPIC_API_KEY=...

trialmark init classification                 # or qa, extraction, summarisation, calculation
cd trialmark-classification-anthropic
trialmark run config.json                     # the plan and a cost estimate; spends nothing
trialmark run config.json --limit 3 --yes     # a few cases first
trialmark run config.json --by-tag --yes      # the full test
trialmark confusion record.json --test-set tickets.csv
```

Then replace the starter's cases with your own. Each starter's README says how.

## What it does not do yet

Each case is one input and one output, so conversations and agents that call tools are not
supported yet. There is no web dashboard; reports are text, Markdown or JSON. And the
fingerprints catch an accidental change to a test, not a deliberate one: signed records, which
would prove who ran a test and when, are planned.
